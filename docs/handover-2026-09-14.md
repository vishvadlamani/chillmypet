## In one paragraph

Meta Events Manager was showing PageView, ViewContent, InitiateCheckout,
AddToCart and TestEvent, but **no Purchase and no AddPaymentInfo**. Two real
defects came out of it. First, InitiateCheckout was counting views of
`/checkout` rather than checkouts started, inflating it roughly six-fold.
Second, and far worse, the live checkout could take a card payment that the
application never learned about — leaving the order unfulfilled and the sale
reported to Meta by neither the browser nor the Conversions API. Both are fixed
on the branch above. The second fix needs one change in the Stripe dashboard
that no agent can make, and nothing is live until the branch is merged.

## Finding 1 — InitiateCheckout counted page views, not checkouts

**Confirmed.** The guard on the tracking effect in
`apps/storefront/src/routes/checkout/+page.svelte` was a plain `let`, which
lives for exactly one component mount. The cart lives in `localStorage` and
outlives all of them. So a reload of `/checkout`, a back-navigation, a return
visit, or the bounce back from Stripe's cancel URL each reported a fresh
checkout start on the same unchanged cart.

The evidence was in the numbers: **Initiate checkout 114 against Add to cart
18**. A cart cannot be checked out before it is filled, so that ratio is
impossible for a real funnel.

**Fix:** the guard is now keyed on the cart's contents and held in
`sessionStorage`. Re-entering the page with the same lines is silent; a
genuinely different cart, or a new session, fires again. The same guard covers
the GA4 `begin_checkout` push, which was inflated identically.

Expect Initiate checkout to drop sharply after deploy. That is the fix working,
not traffic falling.

## Finding 2 — a paid order the application never hears about

**The code defect is confirmed. The dashboard misconfiguration that triggers it
is not — that is the one thing still to check.**

The live checkout uses Stripe's inline Payment Element (verified on
chillmypet.com/checkout: `paymentsEnabled:true` and a live `pk_live_…` key is
served). That path mints a **PaymentIntent** and never creates a Checkout
Session, so a completed sale emits **`payment_intent.succeeded`**.

`README.md` told whoever set up the webhook to subscribe to
`checkout.session.completed`, `checkout.session.expired` and `charge.refunded`.
That line was written in the commit *"Integrate Stripe: hosted checkout…"* and
was never revisited when checkout moved to the inline form. **It does not list
the event the live flow actually fires.**

Before the fix, `markPaid` was the only code that could set an order to `paid`
and `handleWebhook` was its only caller — no polling, no way to read a payment
intent back. So an endpoint missing that event means:

1. the card **is** charged
2. the order stays `pending_payment` — nobody knows to ship it
3. the receipt reads "processing" forever
4. the browser Purchase never fires (it needs `paid`)
5. the server Purchase never fires (it needs `action === 'order_paid'`)
6. **nothing is logged**, because from the app's side no event arrived

That is a complete, silent loss of the one event the ad account bids on — which
matches the symptom exactly.

**Fix:** `/checkout/success` no longer only waits to be told. Rendering an order
it believes is unpaid, it calls `payments.reconcile()`, which reads the intent
back off Stripe and settles the order when Stripe says it succeeded for the
amount owed. The sale is reported from there, carrying the customer's own
cookies, address and user agent — better matching than the webhook, which is a
request from Stripe and carries none of them.

Both paths now converge on one `settleOrder`, so the amount assertion exists
once, and it refuses an order already marked paid. That refusal is what makes
the two idempotent against **each other**: whichever arrives second reports
nothing, and one sale stays one sale.

**Reconciliation is a backstop, not a replacement.** Someone who closes the tab
at the bank's 3-D Secure step never loads the receipt, and only the webhook will
ever settle that order. The subscription still has to be fixed.

## Finding 3 — the Events Manager list itself was not a bug

The Overview is not a per-page configuration. It lists **everything the dataset
has ever received**, from the whole site. The six events the code fires:

| Event | Fires from | Page |
|---|---|---|
| `PageView` | base snippet on every HTML response, plus each client-side navigation | every page |
| `ViewContent` | product page mount | `/products/dog-life-jacket` |
| `AddToCart` | bundle picker / sticky bar | `/products/dog-life-jacket` |
| `InitiateCheckout` | checkout page, once per cart per session | `/checkout` |
| `AddPaymentInfo` | Place order pressed with a valid form | `/checkout` |
| `Purchase` | receipt page (browser) + webhook or reconcile (server) | `/checkout/success` |

`TestEvent` is **not from this codebase** — it appears nowhere in the source or
its history. It is the event name in Meta's own Events Manager sample cURL,
sent when someone verifies a Conversions API token. Harmless; it just never
drops off the list. Unrelated to `META_CAPI_TEST_EVENT_CODE`, which diverts real
events to the Test Events tab rather than creating an event called TestEvent.

**AddPaymentInfo's absence is still unexplained.** It is independent of Stripe —
it fires in the browser the moment Place order is pressed with a valid form. Its
absence is consistent with nobody having completed the checkout form, which is
also consistent with there being no sales yet. The way to tell: look in Stripe
for successful charges (see below).

proves the handler works and **can never tell you whether Stripe is configured
to deliver it**. A green suite is not evidence of a live subscription.

## What still needs a human

No agent in this session had Cloudflare, Stripe, Turso or Meta credentials, so
none of the following could be done for you.

**1. Merge the pull request — then deploy separately.** `.github/workflows/deploy.yml`
looks like it deploys on any push to `main`, and it is written to. **It has never
once succeeded.** The workflow has run twice in this repo's life (8 Sept on
`claude/cloudflare-access-odjny1`, 14 Sept on `main`) and both runs failed at the
final step with:

```
✘ [ERROR] In a non-interactive environment, it's necessary to set a
  CLOUDFLARE_API_TOKEN environment variable for wrangler to work.
```

`CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` were never added as repository
secrets, so they resolve empty. Everything before that step passes — install,
typecheck, tests and build all succeed in under 40 seconds. Production has been
deployed by hand with wrangler instead, which is what the Deploying section of
`AGENTS.md` describes.

So merging lands the code on `main` and **nothing goes live**. Pick one:

- **Fix it properly** (one time, ~2 min): GitHub → Settings → Secrets and
  variables → Actions → New repository secret, add both names above. The token
  needs Workers Scripts edit permission on the account that owns the
  `chillmypet` Worker. Then Actions → Deploy → Re-run jobs. Every merge
  deploys itself from then on, and the "merging is the deploy" model becomes
  true.
- **Ship it now by hand**: from a checkout with Cloudflare credentials,
  `git checkout main && git pull && npm install && npm run deploy`.

**2. Add `payment_intent.succeeded` to the Stripe webhook.**
Stripe → Developers → Webhooks → your endpoint → "Events to send". The full set
the handler acts on is in `README.md` under Payment. Do this even though
reconciliation now covers most cases.

**3. Look for stuck orders.** Stripe → Payments. Any successful charge whose
order was never fulfilled is a real sale that was silently lost. Opening
`chillmypet.com/checkout/success?order=CMP-XXXXXXXX` for one of them will now
settle it — but Meta generally rejects conversions older than about 7 days, so
treat the old ones as fulfilment to fix rather than reporting to recover.

**4. Verify with one real order before running ads.** Place a small order and
refund it. Check all three: Stripe shows the payment, the receipt says *Payment
received* rather than "processing", and Events Manager shows Purchase.

  on push to `main`.
- Primary pixel `1363695699271757` — browser events **and** the Conversions API

  CAPI token is scoped to one dataset.

  which also fires the single server-side PageView.
- Purchase's `event_id` is derived from the order number as
  `purchase-<orderNumber>`, so the browser and server halves dedupe.
- Payments run on a **borrowed Stripe account** that is not ChillMyPet's — see
  the warning in `AGENTS.md`.
- `AGENTS.md` is the living architecture document and takes precedence over this
  snapshot wherever they disagree.
