## In one paragraph

A new USD ad account was created and a new dataset connected to it, but Events
Manager reported no Conversions API activity for it. The cause was not a broken
integration: **the dataset id appeared nowhere in the storefront's
configuration**, so the site had never sent it anything — no server events and
no browser events either. The Conversions API code could only ever report to
one dataset, because a token authorises exactly one, so the new ad account
could not have server-side conversions without taking them from the old one.
The branch above makes the sender fan one event out to several datasets, each
with its own token. The token for the new dataset is verified working against
live Meta. Nothing reaches the dataset until a human sets a Worker secret and
deploys by hand.

## Finding — the dataset was in Business settings, never in the code

`pixelSnippet` in `hooks.server.ts` initialises only the ids it is given, and
`send()` posts only to `META_PIXEL_ID`. `1341978141149107` was in neither
`META_PIXEL_ID` nor `META_EXTRA_PIXEL_IDS`, so it received zero events of any
kind. Meta's "pixel not detected on this website" was accurate.

Checked on the live site the same day:

```
$ curl -s https://chillmypet.com/products/dog-life-jacket \
    | grep -o "fbq('init', '[0-9]*')" | sort -u
fbq('init', '1363695699271757')
fbq('init', '28272021345717397')
```

Two, not three. That is still true until someone deploys.

## What changed — two commits on `claude/nifty-lamport-acfgpa`

`aee9e19` — *Report conversions to every ad account's dataset, not just one*

- `createMetaService` gains `additionalDatasets`, each entry a dataset with its
  own `accessToken` and `testEventCode`. The payload is built once and shared,
  so the SHA-256 per advanced-matching field is not paid per destination, and
  every dataset receives the same `event_id` and dedupes its own server copy
  against its own browser copy.
- Destinations post independently. `sent` is true once any accepted, and a new
  `results` array carries the per-dataset outcome — with more than one
  destination, "it failed" stops being a single answer.
- Datasets pair **by suffix**, `META_PIXEL_ID_2` with `META_CAPI_ACCESS_TOKEN_2`,
  not by position across two lists, where one edit silently mismatches a token
  to a dataset and Meta refuses the events somewhere only Events Manager shows.
- An id whose token has not arrived is still initialised in the browser and
  skipped server-side — the state while a token is being generated.
- `pixelSnippet` now covers the CAPI datasets as well as the extras,
  deduplicated, since a repeat `fbq('init', …)` resets that pixel's state.
- New `packages/ecomwithai/src/marketing/capi.test.ts`, 22 checks, wired into
  `npm test`.

`3d89ff2` — merge of `main`, bringing in the InitiateCheckout dedup fix and the
receipt-side sale settlement so this branch can be deployed without regressing
either. Clean merge; the branch is now zero commits behind `main`.

## Verification that was actually run

Against live Meta, dataset `1341978141149107`, test event code `TEST54768`, so
none of it counted as a conversion:

| Event | Result |
|---|---|
| PageView, ViewContent, AddToCart, InitiateCheckout, AddPaymentInfo, Purchase | `events_received: 1` each, zero `messages` |

Each used the payload its real fire site builds — ViewContent with the slug in
`content_ids`, InitiateCheckout with `num_items`, Purchase with all eight
advanced-matching fields hashed and `event_id: purchase-<orderNumber>`. The
send went through `additionalDatasets` with the primary deliberately
token-less, so the new code path is what carried it.

Offline, on `3d89ff2`: `npm run typecheck` clean, `npm test` all pass,
`npm run check` 466 files / 0 errors / 0 warnings, `npm run build` succeeds.

**Not verified.** `npm run test:e2e` was not run — it needs a dev server and a
seeded database. Its pixel assertions now expect **three** inits, so a local
`.env` needs `META_PIXEL_ID_2`. And the *simultaneous* two-dataset send is
covered by unit tests only: no token for `1363695699271757` was available, so
a live double-send has never been observed. Staging is where that shows.

## What still needs a human

1. **Set `META_CAPI_ACCESS_TOKEN_2`** on the `chillmypet` Worker — `wrangler
   secret put`, or the Cloudflare dashboard. Without it the new dataset gets
   browser events only.
2. **Deploy by hand.** `npm run build && npx wrangler deploy` from
   `apps/storefront` in a checkout with Cloudflare credentials. **CI does not
   deploy** — see `4fe9289`: `deploy.yml` has never once succeeded, because
   `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are not repository
   secrets and resolve empty. Everything before that step passes in under forty
   seconds, which reads as a green deploy. It is not one.
3. **Verify three pixels** with the curl above.
4. **Point the new campaign's ad set at a dataset that has events.** Deploying
   makes the dataset receive data; it does not make the campaign bid on it.
   Until step 2 lands, `1341978141149107` has none — a campaign pointed there
   is optimising against nothing.
5. **Rotate the token.** It was pasted into a chat transcript. Generate a new
   one and repeat step 1.
6. **`npm run sync:framework`** and push the public `ecomwithai` repo, which
   otherwise drifts from `packages/ecomwithai`.

## Known gaps, not addressed here

- **Seven branches carry unmerged commits**, and some contradict this work:
  `claude/audit-remove-gtm-nexn8b` proposes retiring the second Meta pixel, and
  `claude/busy-newton-y5bjdv` and `claude/lucid-dijkstra-v5webd` both carry
  "One pixel, and a check that says when the token is wrong". Three separate
  branches propose removing GTM. Merging any of them without a decision would
  undo part of this change.
- **The Events Manager setup wizard was left unfinished on purpose.** It
  generates a setup document and cannot send an event or enable anything. The
  selections reached during this session described parameters the code never
  sends — data processing options, opt out, subscription id, date of birth,
  gender, external id — and at one point re-templated Purchase as a
  Click-to-WhatsApp messaging conversion. None of it affects delivery; it
  affects diagnostics noise only. The complete set of `custom_data` fields the
  code can emit is six: `currency`, `value`, `content_type`, `content_ids`,
  `contents`, `num_items`.
- **Expect low Event Match Quality on ViewContent, AddToCart and
  InitiateCheckout**, and high on Purchase. Deliberate: `/api/track` rebuilds
  identity from the request's own cookies, IP and user agent and ignores any
  `user_data` in the body, because a public endpoint must not be able to claim
  to be someone else.
